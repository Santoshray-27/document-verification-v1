# Agnitia — Evaluation

All numbers below come from `eval/run_eval.js` running against the live API on
**2026-10-09** (raw output in `eval/results.json`). Nothing is estimated or extrapolated.

## 1. Dataset

40 synthetic files generated by `eval/make_eval_set.py`, ground truth in `eval/labels.csv`.
No real personal data.

| class | n | how it was made |
|---|---|---|
| genuine | 10 | the exact bytes of a freshly issued, signed certificate |
| genuine copy | 5 | writer round-trip · 150 dpi raster · JPEG q70 · greyscale · 3° rotate + noise + downscale |
| altered | 12 | 8 PDF text edits (name ×2, grade ×2, certificate number, issue date, course ×2) + 4 image-space paint-overs (name ×2, grade, course) |
| forged | 6 | 2 rebuilt certificates carrying a **genuine** QR · 3 unregistered-issuer documents · 1 unsigned template copy |
| unverifiable / unable | 1 | a blank page with no QR, no ID and no matching content |
| revoked | 4 | original bytes whose registry record was revoked |

> Label note: documents from an **unregistered** issuer are labelled `NOT ISSUED`, because
> their `doc_id` genuinely does not exist in our registry. `UNVERIFIABLE` is a different
> situation — a *registered* issuer that is suspended or whose key is unavailable — and is
> covered by the end-to-end suite (`A13b`), not by this file set.

## 3. The two things that did not hit target

### Timing: 5.8 s average, not < 5 s

Measured, not guessed. The cost is dominated by OCR: Tesseract runs over a 300 dpi page
render, twice (once for text, once for word confidences), plus a second render for the visual
diff. The cryptographic part is essentially free — the pure hash + signature + registry path
(steps 1–9) completes in single-digit milliseconds; a rejected upload returns in ~1 s.

Obvious next steps, none of them done:
- drop the second `image_to_data` pass and derive confidence from one call;
- OCR at 200 dpi instead of 300;
- run OCR and the visual diff concurrently instead of sequentially;
- skip OCR entirely when the page has extractable embedded text (a digital PDF does not need
  OCR at all — only scans do).

### OCR field accuracy: 83.3%

Denominator = 114 field comparisons across the files that needed them (genuine files skip the
comparison because their hash already matched). The misses are concentrated in fields where
the template prints the value in two places, and in short values like a bare grade, where a
redaction or a raster artefact leaves nothing legible. Two consequences were designed for
rather than papered over:

- a field the registry has but OCR cannot find is treated as a **mismatch** when OCR was
  otherwise reliable (≥70% confidence), and excused when it was not;
- OCR never decides on its own — it only separates `GENUINE COPY` from `ALTERED` after the
  cryptographic checks have already run.

## 4. One real bug this evaluation caught

`altered_04_date.pdf` (the issue date replaced with `2020-01-01`) was first scored as
**GENUINE COPY (High)**. Cause: the edit redacted the date in both places it is printed, so
OCR returned nothing for `issue_date`, and the engine treated a *missing* field as a warning
rather than a mismatch. With every critical field "matching" and SSIM at 0.997, it composed to
GENUINE COPY.

Fix in `verdict.engine.js`: a registry field that OCR cannot find is now a `failed` comparison
when overall OCR confidence is ≥ 70%. Two regression tests were added
(`tests/verdict.test.js`): a redacted field must yield `ALTERED`, and the same missing field
under 42% OCR confidence must still yield `GENUINE COPY`. After the fix the set scored 40/40.

That is a single dataset. The failure mode is documented in `docs/security-notes.md` §10.4.

## 5. Beyond the 40 files

`tests/e2e.js` exercises 33 further assertions end to end against the live API, including the
paths this dataset cannot reach:

- `UNVERIFIABLE` via a suspended registered issuer (`A13b`), and recovery (`A13c`)
- signature failure by flipping one character of a stored manifest (`A20`), then restore
- audit-chain tamper detection and restore (`A28`, `A28b`)
- public-endpoint privacy (`A22`), RBAC (`A24`, `A26`), auth (`A4`, `A5`)
- upload validation (`A17`, `A18`), path traversal (`A29b`, `A29c`), XSS (`A30`), SQLi (`A31`)
- no private key in any response (`A32`)
- rate limiting (`A23`, run separately because it deliberately exhausts the limiter)

Unit tests: `tests/crypto.test.js` (8) and `tests/verdict.test.js` (24) — **32 unit tests,
33 e2e assertions, 40-file evaluation set**.

## 6. Reproduce

```bash
# 1. services up (see README)
# 2. build the dataset
python3 eval/make_eval_set.py
# 3. score it
node eval/run_eval.js          # writes eval/results.json
# 4. unit + e2e
node --test tests/crypto.test.js tests/verdict.test.js
node tests/e2e.js
```
